# 自建虚拟人像资料设计

## 目标

将人像库的“新建人像”明确为创建 Ark 自建虚拟人像。创建时保留人像图片和名称，并允许用户设置独立性别与基础描述。后续展示、筛选和视频生成应使用持久化性别，不再要求用户把性别编码在人像名称中。

## 数据设计

`custom_portraits` 增加可空的 `gender` 字段，值仅允许“男”或“女”。新建记录必须写入性别；字段保持可空是为了兼容已经注册的自建人像。旧记录没有独立性别时，前端仍可临时从旧名称格式解析，避免现有数据突然显示为未知。

基础描述继续使用 `media_assets.description`。该字段已经跟随上传素材持久化并由自建人像列表返回，不再建立重复字段。

## API 与任务流

`POST /api/portraits/custom` 请求从只有 `assetId` 扩展为 `assetId + gender`。服务端只接受“男”或“女”，并将性别与排队记录事务顺序一致地保存到自建人像记录。Job values 同时记录性别，便于任务审计和恢复，但 Ark `CreateAsset` 仍按官方图片资产协议提交，不伪造上游字段。

列表响应增加可选 `gender`，以兼容旧记录。API 契约变更后重新生成 OpenAPI 文档和前端 SDK，不手工编辑生成文件。

## 界面与交互

创建弹窗标题改为“新建自建虚拟人像”，继续使用现有紧凑 `ToolCreatorModal`。

表单字段依次为：

- 人像图片，必填。
- 人像名称，必填，最多 80 字。
- 性别，必填，使用紧凑原生选择框，仅男、女两个选项。
- 基础描述，选填，最多 300 字，使用多行输入。

创建按钮只有在图片、名称和性别完整时可用。提交成功后清空字段、切换到“自建虚拟人像”列表并继续轮询处理状态。卡片筛选、详情标签和传给创作流程的人像资料优先使用独立性别。

## 迁移与兼容

通过新的 Drizzle migration 增加列，不改写历史 migration，也不修改现有 `.data/yaozuo.sqlite`。已有记录的 `gender` 为 null，仍通过旧名称解析回退；所有新记录必须具备独立性别。

## 错误处理

- 缺失或非法性别由请求 Schema 拒绝，不创建 Job 或自建人像记录。
- 图片、大小、TOS 和 Ark 校验继续沿用现有错误结构。
- 入队失败时保留已记录性别并将记录标记为失败，便于用户查看和排障。

## 验证

- Store 测试验证性别持久化、owner 隔离和旧数据兼容。
- API/页面契约测试验证性别必填、基础描述字段、标题和提交参数。
- 重新生成 OpenAPI 与 SDK，运行数据库迁移校验、相关单测、`make ci`、`bun run typecheck` 和 `bun run build`。
