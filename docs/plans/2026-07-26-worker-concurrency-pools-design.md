# Worker 并发分池设计

## 目标

将异步任务按资源类型分成两个独立的 BullMQ 队列：实际执行 FFmpeg、Remotion 或同类本地媒体处理的任务整单使用 2 个并发；纯网络请求、轮询、下载以及只使用 `ffprobe` 校验的任务共享 40 个并发。

## 方案选择

采用同一 Worker 进程内的两个 BullMQ Worker 实例，分别消费网络队列和媒体处理队列。相比单队列加进程内信号量，该方案不会让等待 FFmpeg 名额的任务占用网络任务 active 槽位，并且限流语义在多个 Worker 进程间仍由 BullMQ 队列边界保持。相比拆成两个独立进程，它不增加部署单元和本地启动复杂度。

## 队列与配置

- 基础队列名仍由 `REDIS_QUEUE_NAME` 配置，默认 `yaozuo-jobs`。
- 网络队列名为 `<基础名>-network`，默认并发 40。
- 媒体处理队列名为 `<基础名>-ffmpeg`，默认并发 2。
- 新配置为 `NETWORK_WORKER_CONCURRENCY` 和 `FFMPEG_WORKER_CONCURRENCY`。
- `WORKER_CONCURRENCY` 只作为旧部署的兼容回退；显式的新配置优先。

## 任务分类

分类器是 `shared/jobs` 下的纯函数，由 API 入队、Worker 恢复和测试共同使用。分类依据是持久化的 `JobRecord.moduleId` 与 `values`，不根据运行时临时状态猜测。

进入媒体处理队列的任务包括：

- 视频切片、片段合并、视频混剪和视频编辑渲染。
- 视频复刻的素材分析和最终合成；提示词改写和仅下载校验的分镜生成留在网络队列。
- 视频创作中会生成、替换、合成、烧录字幕或拼接媒体的操作；纯脚本、分镜文本生成和单独配音生成留在网络队列。
- 通用任务中可能生成本地媒体 Mock 或执行本地媒体处理的类型。

只使用 `ffprobe` 获取时长、编码或尺寸不视为 FFmpeg 处理，因此配音、下载、云端 Seedance 成片校验和 MediaKit 等任务仍进入网络队列。

分类采取保守原则：只要一个任务流程可能执行本地媒体处理，整个任务进入媒体处理队列，避免网络阶段结束后突然突破 2 个本地媒体并发。

## 数据流与生命周期

API 创建并持久化任务后，将完整任务记录交给队列路由器。路由器调用统一分类器并写入对应队列。取消时在两条队列中查找并移除同一任务 ID；队列状态返回两条队列的合计。Worker 启动恢复任务时再次使用同一分类器，确保恢复路径不会改变资源池。

Worker 进程分别创建两个 Redis 连接和两个 BullMQ Worker，共享只读的 `JobProcessor` 与 SQLite Store。关闭流程依次关闭两个 Worker、队列和 Redis 连接，然后关闭 Store。

## 错误处理

- 找不到待入队的持久化任务时直接报错，不默认投递到任意队列。
- 两条队列继续使用相同的失败回写和 Provider 审计逻辑。
- 分类器对未知任务默认使用网络队列；已知可能执行本地媒体处理的通用视频类任务必须显式覆盖并由测试锁定。

## 验证

- 单元测试覆盖典型媒体任务、混合流程、纯网络任务和仅 `ffprobe` 任务的分类。
- 测试两个队列的派生名称、默认并发与旧配置回退。
- 测试入队、移除、状态汇总和恢复均使用相同分类。
- 运行 `make ci`、`bun run typecheck` 和 `bun run build`。
