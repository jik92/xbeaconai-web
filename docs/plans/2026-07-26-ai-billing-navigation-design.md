# AI 账单与用户菜单设计

## 目标

- 将 Header 用户信息入口改为下拉菜单，保留原账号功能，并把“AI账单”和管理员入口移入该菜单。
- “AI账单”使用一个页面，通过 Switch 切换“充值记录”和“消费记录”。
- 账单使用现有真实充值、管理员赠送、任务扣费和失败退款数据，不新增静态或推测记录。

## 导航与路由

- 侧栏不显示“数据账单”或“AI账单”。
- Header 用户下拉保留一个“AI账单”菜单项，点击后导航至 `/billing/ai`。
- 账单使用单一路由和单一页面，不保留两个独立子路由。
- 页面默认显示充值记录；Switch 切换为消费记录时重置到第一页，并只请求当前类型的数据。

## 充值记录

新增受 Bearer Token 保护的用户级充值流水接口。服务端只按当前登录用户查询，并合并：

- `recharge_orders`：现有本地 Mock 充值订单；
- `admin_credit_grants`：管理员为该用户增加的创作点。

统一返回时间、流水 ID、来源、创作点、人民币金额、变更后余额和状态。管理员赠送没有人民币金额，前端显示 `—`。页面使用共享 `DataTable`，列为“时间 / 来源 / 流水号 / 创作点 / 金额 / 变更后余额 / 状态”。

## 消费记录

新增受 Bearer Token 保护的用户级消费流水接口。服务端只按当前登录用户查询，并合并：

- `credit_charges`：任务扣费，显示为负数；
- `credit_refunds`：失败或取消后的退款，显示为正数并标记“已退回”。

流水通过 `jobId` 关联 `jobs`，返回模块 ID、任务标题、任务编号、变更类型、创作点变化、变更后余额、退款原因和时间。页面使用共享 `DataTable`，列为“时间 / AI功能 / 任务 / 类型 / 创作点变化 / 变更后余额 / 备注”。无法关联历史任务时保留任务编号，AI 功能显示“未知功能”，不得丢弃流水。

两类接口按时间倒序返回，并采用页码与每页数量参数，防止长期流水一次加载过多。

## Header 用户下拉菜单

- 用户名按钮改用现有 Radix Popover 基础组件实现下拉菜单。
- 菜单顶部只显示用户名、手机号和当前创作点，不新增宣传或解释文案。
- 保留原账号中心中的“个人资料”“账号与密码”“退出登录”；前两项继续打开现有抽屉表单。
- 所有登录用户都显示“AI账单”，位置在“账号与密码”之后、“管理后台”之前。
- 管理员额外显示“管理后台”，点击后关闭菜单并导航至 `/admin`。
- 从侧栏删除现有“系统管理 / 管理后台”入口，普通用户始终看不到管理员入口。
- Header 中现有充值、帮助和通知入口保持不变。

## 页面与状态

- 统一页面采用全高白色工作区，主标题为“AI账单”，标题行右侧放置“充值记录 / Switch / 消费记录”，不使用装饰卡片或标题下说明文案。
- Switch 使用现有 Radix/shadcn 组件，未选中的一侧保持普通文本，当前侧使用较强文字色；控件具有明确的无障碍标签。
- 加载、空数据和失败状态通过 `DataTable` 统一展示。
- 页码改变后请求对应服务端分页；接口失败不伪造流水，也不静默回退。
- 创作点数字使用本地千分位格式，人民币金额仅对充值订单展示。

## API 与安全

- 在 `server/app.ts` 中以 Zod/OpenAPI 定义两个账单列表接口和统一分页结构。
- Store 查询使用 Drizzle ORM，禁止 raw SQL；所有查询条件均从鉴权上下文读取 `userId`。
- API 契约变更后重新生成 OpenAPI 与前端 SDK，前端不手写 DTO。
- 当前充值保持明确的本地 Mock，不引入真实支付渠道。

## 测试与验收

- Store 测试覆盖用户隔离、两种充值来源、扣费、退款、排序、分页和历史任务缺失。
- API 契约测试覆盖两个受保护路由、分页参数和响应字段。
- 前端契约测试覆盖统一路由、Switch、两种账单表格和用户下拉中的账单入口。
- Header 测试确认账号原有功能仍可达，管理后台已从侧栏移除并仅在管理员下拉菜单出现。
- 运行相关单测、OpenAPI/SDK 生成、`make ci`、`bun run typecheck` 和 `bun run build`；默认不运行 E2E。
